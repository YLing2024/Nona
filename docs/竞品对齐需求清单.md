> 对标对象：

> - `H:\AiWorkspace\opencode\rikkahub`（原生 Android LLM 客户端，约 11.4 万行 Kotlin，上架 Google Play）

## 1. 系统性差距分析（为什么差 10 倍）

### 1.1 体量与投入对比

| 维度 | Nona（当前 dev_2.0） | Kelivo | RikkaHub |
|---|---|---|---|
| 代码量 | ~3.6 万行 Dart | ~33.6 万行 Dart（含 1.9 万行自维护 fork 依赖） | ~11.4 万行 Kotlin |
| 功能模块 | lib 扁平 11 目录、28 屏、74 服务 | core(159)/features(150)/desktop(51) 三层，21 个 feature | 8 个 Gradle 多模块 |
| 迭代 | v1.3.0，10 个 commit，约 10 天 | v1.1.17+61 构建 | 多版本长期迭代 |
| 数据层 | 裸 sqlite3 手写 SQL + 条件导出双实现 | drift 2.34 + build_runner 代码生成 + 23 张表 + 收据化迁移 | Room + FTS5 + jieba 分词 |
| 网络层 | http 包手包 | dio 5.9.2 + 拦截器 + socks5 代理 | OkHttp/Retrofit |
| 语音 | 系统 TTS（flutter_tts） | 8 家网络 TTS + 6 家 ASR + sherpa 本地 | 11 家 TTS + 5 家 ASR |
| 搜索 | 5 引擎 | 16 引擎 + Key 轮换 + 用量 | 19 引擎 + QuickJS 自定义脚本 |
| 备份 | ZIP 打包整体恢复 | 25 文件恢复状态机（staging/cutover/receipt/durability FFI） | Room 快照 |
| 桌面 | 无 | 51 文件（无边框窗口/托盘/热键/拖放） | — |

### 1.2 三大差距根因

**差距一：工程架构（P0，约 30% 差距）**
- Nona：`lib/` 扁平 11 目录；数据库层 `nona_database.dart` 手写 `CREATE TABLE` + `PRAGMA user_version` 迁移数组（`schema_migrations.dart`，6 个版本函数）；平台差异靠 4 组条件导出（db/env/fs/session_persistence/network_log_store 均 `*_io.dart` / `*_web.dart` / `*_stub.dart`）；无桌面基座、无统一网络层、无 CI。
- Kelivo：drift 生成类型安全 DAO、`GenerationRun` 状态机表（乐观并发 state_revision）、收据化数据迁移（business/hive/database 三类收据 + fsync 原子发布）、`LatestWinsCheckpointWriter` 等通用基础设施。**Nona 每加一个功能都要重造基础件，Kelivo 只需在底座上加一张表。**

**差距二：功能广度（P1，约 40% 差距）**
- Kelivo 21 个 feature 中 Nona 缺失/薄弱：搜索 16 引擎（Nona 5 个）、网络 TTS 8 家（Nona 仅系统）、ASR 语音输入（Nona 无）、快速短语/指令注入/标签（Nona 无）、多 Key 管理 UI、服务商分组、二维码分享/扫描、统计热力图、建议气泡、引用出处面板、选择模式、助手正则、提示词模板、后台生成、系统分享入口等。
- Nona 已具备且扎实的：三协议适配（`protocol_adapter.dart` 抽象极干净）、SSE 状态机、tiktoken 精确估算、知识库 RAG、记忆/世界书、8 种导入、SigV4 S3、网络日志脱敏。

**差距三：平台深度（P1，约 30% 差距）**
- Kelivo desktop/ 51 文件：无边框窗口、窗口状态持久化、托盘、7 个全局/应用内热键、桌面右键菜单体系、Popover 家族、HTML WebView 预览。Nona 无。
- Android：Kelivo 有 flutter_background 前台服务 + 通知 + PROCESS_TEXT 分享入口；RikkaHub 有 proot workspace、baseline profile。Nona 无。
- iOS：Kelivo 有 BGTask + Live Activity + 通知通道。Nona 无。

### 1.3 实施策略

按「追平基线（A~J）→ 超越项（X）」宏观两阶段实施；每阶段内部只遵循依赖顺序（见第 5 章），不设时间排期。所有需求落位到 A-02 建立的新目录结构，避免二次迁移。

### 1.4 超越机会分析（竞品源码确认的空白）

基于对两家竞品全部源码的精读，确认以下能力在竞品中**不存在或只是雏形**，构成 Nona 的超越空间：

| # | 竞品空白 | 源码证据（确认不存在） | Nona 超越项 |
|---|---|---|---|
| 1 | 无自动化工作流 | kelivo 无 task/schedule/trigger 任何概念；rikkahub workspace 仅是 proot shell 沙箱（`workspace/` 模块只有 RootfsInstaller/ShellRunner，无任务编排） | X-01 自动化工作流引擎 |
| 2 | 无智能模型路由 | kelivo 只有 7 个手动默认模型槽（`default_model_pane.dart` 的 Chat/Title/Summary/Suggestion/Compress/Translate/OCR 卡），无按任务/成本/延迟自动路由 | X-02 智能模型路由 |
| 3 | 导入只有"能导"没有"好导" | kelivo/rikkahub 均无跨格式导入（rikkahub 无导入；kelivo 仅自家 hive 迁移）；Nona 已有 8 格式导入，但无质量报告/去重/合并 | X-03 导入武器化 |
| 4 | 无多设备实时同步 | kelivo `data_sync.dart`（2203 行）与 Nona `sync/` 均为"备份上传/下载"式同步，无实时双向增量同步 | X-04 多设备实时同步 |
| 5 | 无全离线链路 | kelivo ASR 默认云服务（`cloud_asr_service.dart` 1550 行），sherpa 需手动下载且仅语音；embedding 全部云端；无端到端离线方案 | X-05 本地优先全离线链路 |

> 判定标准：超越项必须是「竞品仓库中 grep 不到任何实现」的功能，而不是「竞品有但做得好一点」的改良。X-01~X-05 全部通过该标准。

## 2. 优先级定义与工作量约定

| 级别 | 含义 | 效果 |
|---|---|---|
| P0 | 架构地基 / 高频核心体验 / **超越项**（X 域全部），不做无法追赶 | 追平 + 超越 |

| P2 | 亮点差异化 | 增强 |

工作量单位：人天。A~J 追平基线约 **130 人天**；X 超越项约 **30 人天**；合计约 **160 人天**。

## 4. 详细需求与技术方案

### A. 工程架构与基础设施

---

#### A-01 数据库层引入 drift（P0，5 人天）

**现状（Nona 源码级）**
- `lib/db/nona_database.dart:17-129`：`NonaDatabase` 封装，`open()` 幂等（`_opening` 记忆化 Future），失败降级 `openInMemory()`；`_initSchema()` 手写 3 张基础表（sessions/messages/message_tokens）+ `PRAGMA foreign_keys=ON` + WAL + `busy_timeout=5000`。
- `lib/db/schema_migrations.dart:5-34`：`typedef SchemaMigration = void Function(Database db)`，数组下标即目标版本-1，共 6 个迁移（v1 消息明细列、v2 压缩块/用量/媒体、v3 知识库 7 表、v4 记忆、v5 世界书），`_addColumnIfMissing` 幂等补列。
- 平台差异：4 组条件导出 `*_io.dart` / `*_web.dart` / `*_stub.dart`（db/env/fs），Web 端 `NonaDatabase.open()` 返回 null，服务层回退文件/内存/SharedPreferences。
- 持久化分层：`SessionPersistenceSqlite` → 降级 `SessionPersistenceIo`（文件）→ 内存；`SessionService._persistChain` 串行写链；`SessionManager.persist()` 500ms 防抖。
- 服务层直接用 `sqlite3` 裸 API：`session_persistence_sqlite.dart`（536 行手写 INSERT/SELECT/事务）、`knowledge_base_service.dart`（bigram 倒排/向量 BLOB）、`search_service.dart`、`usage_stats_service.dart`（usage_daily 预聚合）。

**竞品参考（kelivo 源码级）**
- drift 2.34 + build_runner；`lib/core/database/app_database.dart`：`NativeDatabase.createInBackground`（isolate 内打开，注册执行 isolate 探针函数），`MicrosecondDateTimeConverter` 全表微秒时间；PRAGMA：wal_autocheckpoint=1000、journal_size_limit=16MiB、busy_timeout=5000、synchronous=NORMAL。
- 23 张表覆盖全部业务（conversation/message/message_part/asset/generation_run/assistant/provider/mcp_server/world_book/quick_phrase/search_service/tts_service/instruction_injection/assistant_tag/preference…），实体表统一 `payload JSON` 模式。
- 关键表：`MessagePartRows`（text/reasoning/tool_call/tool_result 四 kind 部分表，消息内容权威）、`GenerationRunRows`（生成运行状态机：preparing→requesting→streaming⇄waiting_tool→终态，`transition()` 乐观并发 `WHERE id=? AND state=? AND state_revision=?`，`checkpoint()` 序列号）。
- 迁移哲学：schema 1 为唯一契约，**不做渐进 ALTER**，升级靠备份/恢复；业务迁移走「收据」（`business_migration_complete_v1` 等）单事务写后读校验 + `wal_checkpoint(FULL)` 屏障。
- 连接契约校验：`validateConnectionContract()` 启动时校验 user_version/journal_mode/foreign_keys/busy_timeout/synchronous 等 7 项。

**技术方案**
- 目标：不推翻现有 SQLite 数据，用 drift 重构数据访问层，获得类型安全 + 迁移工具链 + Web 端统一（`drift` 的 `WasmDatabase`），同时保留 Nona 特有的「文件存储降级链」。
- **表映射清单**（drift 表 → 现有表，字段逐列对齐，含索引）：

| drift Table | 现有表 | 备注 |
|---|---|---|
| `Sessions` | sessions | 含 summary/summary_tokens/memory 迁移列 |
| `Messages` | messages | 含 sent_at、tool_calls_json 等全部迁移列；加 `MessageParts` 从属表（`parts_json` 或独立行，见下） |
| `MessageTokens` | message_tokens | bigram 倒排 |
| `CompressedBlocks` | compressed_blocks | |
| `UsageDaily` | usage_daily | |
| `GenMedia` | gen_media | |
| `KbLibraries/KbDocuments/KbChunks/KbBigrams/KbVectors` | kb_* | |
| `Memories` | memories | |
| `WorldBookEntries` | world_book_entries | |
| `ProviderGroups`、`SearchKeys`、`QuickPhrases`、`InstructionInjections`、`Tags` | 新增 | 供 C-03/G-04/G-05/G-06 使用（先行建表） |
| `GenerationRuns` | 新增 | 供 B-06 使用（先行建表，含 state/state_revision/checkpoint_seq） |

- **消息内容权威化**（对齐 kelivo MessagePartRows）：`Messages` 表新增 `parts_json` 列（text/reasoning/tool_call/tool_result 分段），写路径流式期间只写 parts，终态回写 content 镜像（`includeContent: !isStreaming`）；v6 迁移 `_addColumnIfMissing(parts_json)`，旧消息 parts_json 为 null 时读 content 兼容。
- **迁移策略**：`MigrationStrategy` 内 `beforeOpen` 钩子中：若 `user_version < 6` 走现有 `applySchemaMigrations`（保留数组式迁移作为 drift 迁移工厂的 one-time 封装），后续版本用 drift 生成式迁移（`stepByStep` + schema json 测试）。**不学 kelivo 的「拒绝渐进迁移」**——Nona 已有真实用户数据。
- **Web 端**：`WasmDatabase`（drift 官方 web 支持，sqlite3 wasm 单文件加载），`NonaDatabase.open()` 在 Web 返回 WasmDatabase；现有 `*_web.dart` 回退逻辑保留为 Wasm 加载失败兜底。
- **降级链保持**：drift 打开失败 → 现有文件/内存回退逻辑不动；`SessionPersistence` 接口不变（`readAll/writeAll/writeSession/deleteSession` + `IndexedSessionSearch`），实现体替换为 drift DAO。
- **类与接口签名**：
```dart
// lib/core/database/nona_app_database.dart
@DriftDatabase(tables: [Sessions, Messages, MessageTokens, ... , GenerationRuns])
class NonaAppDatabase extends _$NonaAppDatabase {
  NonaAppDatabase(super.e);           // 由 open() 工厂创建
  @override int get schemaVersion => 7;
}
class NonaDatabaseFactory {
  static Future<NonaAppDatabase?> open({bool forceMemory = false}); // 保留 wasFresh 语义
}
// DAO 层（lib/core/database/dao/）
class SessionDao { Future<List<ChatSession>> readAll(); Future<void> upsert(ChatSession s); Future<void> delete(String id); Future<List<MessageSearchHit>> search(String q, {int limit}); }
class MessageDao { Stream<ChatMessage> watchBySession(String id); Future<void> insertParts(String messageId, List<MessagePart> parts); }
class GenerationRunDao { Future<GenerationRun> create(); Future<void> transition(String id, state, {expectedStateRevision}); Future<void> checkpoint(String id, int seq); Future<void> resetStale(); }
class MiscDao { /* usage_daily、kb_*、memories、world_book、quick_phrases、tags、provider_groups */ }
```
- **替换顺序**：`session_persistence_sqlite.dart`（会话/消息/搜索）→ `usage_stats_service.dart` → `knowledge_base_service.dart` → `world_book_service.dart` → `memory_service.dart`。每替换一个域跑该域测试，最后删除旧 `nona_database.dart` 中已迁移表的手写 SQL（保留 `db.dart` 条件导出给未迁移处）。
- **风险**：drift 生成物与手写 SQL 语义差异（尤其 `INSERT OR REPLACE` vs drift `insertOnConflictUpdate`、事务嵌套）；对策：每个 DAO 替换后做「新旧双实现读写一致性测试」（同数据双写对比）。

#### B-06 流式生成稳定性（checkpoint 持久化）（P0，5 人天）

**现状（Nona 源码级）**

**竞品参考（kelivo 源码级）**
- `latest_wins_checkpoint_writer.dart`（94 行）：`add(value)` 覆盖 `_pending` + 懒启动 `_drain()`，两次写间最小间隔 250ms，失败记录并后续立即抛错；`barrier()` 等待排空；`finalize(writeFinal)` 关闭接收、丢 pending、等 drain 后终态写（**终态写不被中间 checkpoint 超越**）。
- `GenerationRunRows` 状态机：`transition()` 乐观并发（`state_revision`），`checkpoint()` 递增 `checkpoint_seq`；`resetStaleStreamingState()` 启动时把遗留 active run 置 interrupted(error_code='app_restart')，`is_streaming=true` 的消息按 parts 权威回填 content/reasoning 后清标志。

**技术方案**
- 新建 `lib/features/chat/services/checkpoint_writer.dart`（端口 latest-wins 设计）：
```dart
class LatestWinsCheckpointWriter<T> {
  LatestWinsCheckpointWriter(this._write, {Duration minInterval = 250ms});
  void add(T value);                 // 覆盖 pending + 懒启动 drain
  Future<void> barrier();            // 等待排空，失败即抛
  Future<void> finalize(T finalValue); // 终态写，丢弃中间
}
```
- 落库时机：`chat_run_orchestrator.sendText` 流式阶段每帧（现有 scheduleFlush 处）把「当前 content + reasoning + toolEvents 快照」经 writer 写库：**增量 UPDATE 消息行**（content/reasoning_content/tool_calls_json/interrupted/failed + 新列 `streaming_state` = 'streaming'）。避免每次重写整会话（复用 `session_persistence_sqlite` 的 `writeSession`？太重——需新增 `updateMessageIncremental(sessionId, messageId, fields)` DAO，A-01 的 MessageDao 承担）。
- `GenerationRuns` 表（A-01 建表）：`beginSendGeneration → transition(preparing→requesting→streaming)`、每 checkpoint `checkpoint(seq)`、终态 `transition(completed/failed/cancelled, expectedRevision)`；失败重试用乐观锁校验。
- 启动恢复：`main.dart` 初始化后 `resetStaleStreamingState()`：遗留 streaming 消息 → 回填已存内容、置 `failed=true`（错误文案「生成被中断」），UI 显示「可重试」按钮（复用现有 regenerate 通道）。
- 断线自动续传：SSE 断开时若服务器支持 `Last-Event-ID`（OpenAI 不支持，跳过），策略=保留已生成内容标记 `interrupted` + 一键重试（对齐 kelivo：保留部分内容而非清空）。
- 退出冲刷：`app_exit_flush.dart`（desktop 退出钩子注册表，A-03 托盘退出时调用 `flushAll`：writer.barrier + 网络日志 flush）。

**分步实施**
1. checkpoint writer + MessageDao.updateMessageIncremental + GenerationRuns 表。
2. 编排器接入（流式阶段写、终态 finalize）。
3. 启动恢复 + 遗留消息 UI 处理。
4. 退出冲刷。

**验收标准**：流式中 `kill` 进程（Windows 任务管理器强杀）→ 重启后消息保留、内容为最后 checkpoint 状态、可重试；连续 100 次 checkpoint 无 SQLITE_BUSY 丢失（注入 busy 测试）。

class Workflows { String id; String name; String triggerJson; String actionsJson; bool enabled; String? agentId; DateTime updatedAt; }

#### X-02 智能模型路由（P0，6 人天）

**现状（Nona 源码级）**
- 路由原料已齐：`model_capability_service.dart`（能力表 + `contextWindowFor` 前缀匹配）、`price_service.dart`（`costFor` 逐模型成本）、`usage_stats_service.dart`（usage_daily 有调用量与 token）、`model_resolver.dart`（`resolveFirstAvailable` 手动回退链）。
- 但选模型全部是手动：`model_config_screen.dart` 7 类默认模型槽（聊天/标题/摘要/翻译/OCR/对比/图片），无自动决策。

**竞品空白（源码证据）**
- kelivo `default_model_pane.dart`（1292 行）：7 张模型卡全部是**手动固定选择**；`ModelRegistry.infer` 只做能力推断，不做选择决策。
- rikkahub：Settings 里 `chat/fast/title/imageGen/translate/suggestion/ocr/compress` 同款手动槽。

**技术方案**
- `ModelRouter`（纯函数核心，易单测）：
```dart
enum RoutingTask { chat, summary, title, translate, ocr, embedding, imageGen }
class RoutingRequest { RoutingTask task; int inputTokens; double costWeight; // 0=纯成本 1=纯速度
  Set<String>? providerAllowlist; Set<String>? modelAllowlist; bool requireReasoning; }
class ModelRoute { String? providerId; String? modelId; String reason; }  // 全 null = 无可行模型
class ModelRouter {
  ModelRoute resolve(RoutingRequest r, ModelRouterContext ctx);  // ctx 注入能力表/价格表/延迟样本
}
```
- 决策流程：候选 = ctx 中能力满足（contextWindow ≥ inputTokens、multimodal/reasoning 按需）+ 白名单过滤 → 按 `score = costWeight * normalizedCost + (1-costWeight) * normalizedLatency` 取最小 → 输出 reason（"成本最低：gpt-4o-mini ￥0.0001/次"）。
- 延迟样本：`usage_stats_service` 扩展 `route_events` 表 `(task, provider_id, model_id, success, elapsed_ms, cost)`，写入点 = 每次任务完成（复用 `recordSessions` 通道加字段）；无样本时 latency 权重按未知处理。
- 接入：title/summary/translate/ocr 四类槽提供「自动」选项（默认开启路由，失败回退手动槽 → resolveFirstAvailable）；chat 槽提供「建议」按钮（不自动切换，展示推荐 + 理由 + 成本对比），避免改变用户主聊天习惯。
- 建议面板：设置 → 模型路由（每任务自动/固定切换 + 最近 30 天「手动 vs 路由推荐」成本差统计）。

**分步实施**
1. Router 核心 + 单测（构造能力/价格/延迟假数据）。
2. route_events 埋点 + 延迟样本。
3. 四类任务接入自动路由 + 回退链。
4. 建议面板。

**验收标准**：成本优先场景下路由模型实际成本 ≤ 手动默认（用历史数据回放验证）；回退链在路由失败时正确降级；建议面板数字与 usage_daily 一致。

#### X-03 导入武器化（质量报告/去重/合并）（P0，4 人天）

**现状（Nona 源码级）**

- 现状只到"能导"：`import_wizard_screen.dart` 直接导入，`BackupImportResult` 只有 `failedItems` 计数，无报告/预览/合并。

**竞品空白（源码证据）**
- rikkahub：全库无任何导入功能（`app/` 无 importer）。
- kelivo：仅有自家 hive→sqlite 迁移（`hive_to_sqlite_migration_*.dart`），无第三方导入。**跨格式导入 + 质量报告在竞品中完全空白**。

**技术方案**
- `ImportReport` 结构化：
```dart
class ImportReport {
  String sourceFormat; int sessions; int messages;
  int succeeded; List<ImportFailure> failures;          // {index, reason, preview}
  QualityMetrics quality;   // {timestampCompleteRate, multimodalPreserved, toolMessagesPreserved}
  List<DuplicateHit> duplicates;  // {hashSessionId, existingTitle, matches: n, suggested: skip|overwrite|copy}

// 生成：importFromBytes 增加 parseOnly 模式（只解析不落库），逐条产出报告
```
- 重复检测：`stableSessionId` 哈希 vs 现有会话 id 集合（`session_service` 提供 `containsId`）→ 三选一动作（跳过/覆盖/复制）。

- 服务商/Agent 合并增强：当前 importer 不含服务商——扩展 `provider_service.mergeImported`（同名按 baseUrl 匹配：追加模型列表合并，key 保留本地）。

**分步实施**
1. parseOnly 模式 + ImportReport 生成。
2. 重复检测 + 去重策略。
3. 向导预览 UI。
4. 服务商合并。

**验收标准**：8 格式各输出完整报告（构造含坏记录的样例）；重复导入可检出并三选一处理；勾选导入结果正确。

#### X-04 多设备实时同步（P0，8 人天）

**现状（Nona 源码级）**
- `sync/sync_service.dart`：只有 `uploadBackup/listBackups/restoreBackup/deleteBackup`（WebDAV/S3），`restoreBackup` 是覆盖式/补集式合并——**单向备份，无增量、无冲突处理**。
- 可复用件：`sync_clients.dart` 的 WebDAV `PROPFIND`（`getlastmodified` 排序）可做指针枚举；`SessionManager.persist` 的 500ms 防抖是变更埋点位置；A-01 后 DAO 统一写路径可挂 change log。

**竞品空白（源码证据）**
- kelivo `data_sync.dart`（2203 行）：备份打包 + WebDAV/S3 上传 + 恢复（overwrite/merge），**无增量变更日志、无设备概念、无冲突**。
- rikkahub：无同步功能（仅备份文件导出）。

**技术方案（无服务器约束，WebDAV/S3 做传输层）**
- **变更日志**：drift 表 `change_log (entity_type, entity_id, op, ts_micros, payload_hash)`；写入埋点：`session_manager._flush`（会话）、`settings_service.save`、`provider_service.save`、`agent_service.save`（A-01 后统一收口在 DAO 层 `afterWrite` 钩子）。
- **增量协议**（自定，存于远端）：
```
sync/meta.json              {schema: 1, devices: {"dev-a": {...}, ...}}
sync/dev-a/changes-00001.jsonl   # [{entity, id, op, ts, payload}...] 每文件≤200 条
sync/dev-a/head.json         {lastSeq: 42, lastTs: ...}
```
- `SyncEngine`：
```dart
class SyncEngine {
  Future<SyncResult> pull();   // 枚举远端 devices → 读各自 head 之后的 changes → 合并
  Future<SyncResult> push();   // 本地 change_log 按 seq 追加写远端文件 + 更新 head
  // 合并规则：同 entity 按 ts_micros last-write-wins；conflict 判定：同 entity 同窗口双端都改 → 写入
  //   conflict_log（保留双版本，UI 解决）
}
```
- 触发：启动时 + 手动 + 定时（节流：桌面每 5 分钟，移动端依赖 I-01 后台窗口）；断网自动跳过下次补传（记录 lastSyncAt）。
- 冲突 UI：设置 → 同步（设备列表/各设备 lastSeq/待拉取数/冲突列表：预览两个版本 → 保留 A/保留 B/都保留）。
- 安全（可选开关）：payload 用 AES-GCM 加密（`cryptography`，密钥存 `secure_credentials_service`，设备首启交换密钥提示）。
- 与 G-01 关系：X-04 是增量同步，G-01 备份仍是全量兜底（恢复/迁移用）。

**分步实施**
1. change_log 表 + 埋点。
2. 增量协议 + push/pull。
3. 合并/冲突判定 + 冲突 UI。
4. 触发调度 + 设备管理 UI。
5. 加密开关。

**验收标准**：双设备（本地起两个数据目录模拟）互导会话/设置变更；断网重连后增量补齐；同会话双端编辑产生冲突并可在 UI 解决；数据可回滚到冲突前。

#### X-05 本地优先全离线链路（P0，6 人天）

**现状（Nona 源码级）**
- 已离线：token 估算（tiktoken 词表内置）、知识库关键词检索（bigram）、全文搜索。

**竞品空白（源码证据）**
- kelivo：sherpa ASR 需手动下载模型（`sherpa_model_manager.dart`），**无本地 embedding**（全部走 provider API），无「离线模式」概念。
- rikkahub：全部云端（ASR/TTS/搜索/embedding 均 provider 化）。

**技术方案**
- **本地 embedding**：依赖 `onnxruntime` 包 + bge-small-zh-v1.5（~15MB 量化）或 all-MiniLM（~23MB）；
  `EmbeddingProvider` 抽象（`knowledge/embedding_provider.dart`）新增实现：
```dart
class LocalEmbeddingProvider implements EmbeddingProvider {
  // 模型文件管理：复用 E-04 SherpaModelManager 模式（models.json/可取消下载/Isolate 解压/原子安装）
  // embed/embedBatch：Isolate.run 执行 ONNX 推理（batch 16 沿用现有分组），dim=384
  // 向量入库：kb_vectors 已有 dim 字段（Float32Codec 编解码带 dim）——检索时按 dim 过滤，新旧向量共存不冲突

```
- **离线模式总成**：`settings_service` 加 `offline_mode`；开启后各服务降级链收口：
  - embedding：Local → 无本地模型时提示下载（不静默用云端）；
  - 搜索：免费引擎（Bing/DDG）→ 失败提示离线；
  - ASR：Sherpa（E-04）→ 未装模型提示；
  - TTS：系统 TTS 兜底；
  - `connectivity_plus` 断网自动降级 + 顶栏「离线」徽标（断网时不弹错误，统一显示离线文案）。
- 性能目标：1 万块全量向量化 < 2 分钟（Isolate + 批处理）；单条嵌入 < 50ms。
- 卖点包装：设置 → 隐私页「离线能力」清单（哪些功能已离线/可离线/需下载模型）。

**分步实施**
1. LocalEmbeddingProvider + 模型管理（依赖 E-04 先建模型管理器骨架）。
2. 嵌入接入知识库向量化/检索。
3. 离线模式开关 + 降级链收口 + 徽标。
4. 隐私页展示。

**验收标准**：完全断网（拔网线/飞行模式）下「导入知识库 → 本地向量化 → 检索 → 聊天引用」全链路可用；新旧维度向量共存检索正确；离线模式与网络检测联动。

## 5. 宏观实施顺序与完成态（不设节奏）

> 本清单只定义两件事：**实施顺序**（依赖关系，不可违背）与**完成态**（验收什么算达标）。不排期、不切迭代——宏观目标只有一个：**全部落地后 Nona 超越竞品**。

**阶段一：追平基线（A~J，49 项）**

**阶段二：超越项（X，5 项）**
- X-03（导入武器化）不依赖任何其他 X 项，可最早落地——现有 8 importer 是唯一原料。

- X 项之间无依赖，可各自独立落地。

### 5.2 完成态定义（超越验收矩阵）

| 完成态指标 | 判据 | 对应需求 |
|---|---|---|
| 功能覆盖 | 竞品功能矩阵（kelivo 21 feature / rikkahub 8 模块的公开能力）逐项可对照 Nona 实现 | A~J 全部 |
| 独有能力 | 5 项 X 功能在竞品仓库 grep 不到任何实现（1.4 节判定标准），Nona 全部落地 | X-01~X-05 |

| 质量门槛 | 第 6 章全部通过 | 通用 |

**完成态结论**：当表中 5 项 X 全部落地且 A~J 全部通过验收时，Nona 在「功能矩阵覆盖 + 5 项独有能力 + 六平台 + 性能基线」四个维度上均不存在竞品具备而 Nona 不具备的能力，即构成超越。此结论不依赖时间节奏，仅依赖清单完整落地。

## 7. 有意保留的差异（不做）

- 不 fork 维护第三方依赖（kelivo 维护 6 个 fork；Nona 用上游，仅必要才 fork）——这不影响超越：fork 是维护成本不是用户能力。
- 不做 proot Linux 工作区（RikkaHub 亮点）：X-01 自动化工作流覆盖其「让 LLM 执行任务」的价值主张，且不要求 root 与 rootfs 下载。
- 不做 QuickJS 自定义搜索脚本（RikkaHub 特性，小众）：D-01 的 16 引擎 + X-02 路由已覆盖搜索的实用价值。
- 不学 kelivo「拒绝渐进式数据库迁移」（Nona 有真实用户数据，必须平滑升级）。
- 方言矩阵（vendor 推理参数特判）保持 P2：与超越无关，属深度打磨。
